## 2. Service Worker Forensic Trace

1. **What gets precached?** All core HTML, CSS, JS, JSON configurations, and app icons as explicitly listed in `STATIC_ASSETS` in `service-worker.js`.
2. **What is intentionally NOT cached?** Firestore and Firebase Identity API calls are completely bypassed by the service worker fetch handler.
3. **Is every JS module required for startup cached?** Yes, all imported modules (`app.js`, `ui.js`, `storage.js`, engines) are present in the list.
4. **Is every CSS/HTML dependency available offline?** Yes, `index.html`, `offline.html`, and `css/styles.css`, `css/responsive.css` are cached.
5. **Are imported modules reachable offline?** Yes, because they are precached during the `install` phase.
6. **What happens when a cache is stale?** The browser will use the cache (because of Cache First strategy for `STATIC_ASSETS`). However, when `APP_VERSION` is updated in `utils.js`, `pwa.js` registers `service-worker.js?v=X`. This forces the browser to re-download the service worker, triggering a new install phase that downloads all assets into the new cache, followed by an activate phase that deletes the old cache. 
7. **What happens after APP_VERSION changes?** The new service worker installs, caches fresh assets, and skips waiting. Old caches are purged. The client then needs a reload to grab the new assets from the new cache.
8. **Are old caches deleted?** Yes, in the `activate` event, the SW deletes any cache starting with `CACHE_PREFIX` that does not match `CACHE_NAME`.
9. **What happens when service-worker.js itself changes?** The browser detects a byte-diff and installs the new version.
10. **What happens if an asset is missing from STATIC_ASSETS?** The `fetch` event will attempt to load it from the network. If offline, it will fail (unless it was previously cached by a dynamic caching rule, but we don't have dynamic caching for missing static files—we rely on Network First for non-static files).
11. **What happens if an asset returns 404?** The `install` phase would fail if a precache asset is missing. During runtime, it returns 404 to the app.
12. **Does navigation work with no network?** Yes, navigation requests (e.g. reloading the page) will hit the network first (as per the code: `event.request.mode === 'navigate'`). If offline, they fall back to the cache (e.g. `index.html`). If cache misses, it returns `offline.html`. Note: `index.html` is in `STATIC_ASSETS`, so the first `if (isStatic)` block actually catches it and uses Cache First instead of Network First. This is a crucial observation.
13. **Does Firebase failure prevent the local application shell from loading?** No, Firebase Auth state observer simply skips loading cloud state if offline. The local application shell will render because local state is loaded first (`initLocalState`).

### Forensic Discovery: Cache First vs Network First for Navigation
The service worker has this logic:
```javascript
const isStatic = STATIC_ASSETS.includes(url.pathname) || url.pathname === '/';
if (isStatic) {
  // Cache First
}
```
Because `/` and `/index.html` are in `STATIC_ASSETS`, they use the **Cache First** strategy. The specific block for `event.request.mode === 'navigate'` (Network First) is therefore skipped for the main entry points! This means the user will always see the cached version of `index.html` regardless of network connectivity, unless `APP_VERSION` changes and triggers a new SW install. This is correct PWA behavior.
