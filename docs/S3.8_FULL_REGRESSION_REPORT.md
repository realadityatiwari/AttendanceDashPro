## Cross-System Combination Tests

### A. Attendance mutation + Quiz recalculation + Date navigation
**Observed Behavior:** Marking attendance immediately updates the `AppState`, which triggers a unified `recalculateAndRender()` cascade. The Attendance Engine calculates the new aggregates, and the Quiz Engine derives updated eligibility metrics based on the current active quiz tab. Date navigation properly segregates past data from future (Simulation) scenarios. State remains coherent.

### B. Academic Event + Attendance + Date navigation
**Observed Behavior:** Adding an event (e.g., `EXTRA_LECTURE` or `CLASS_CANCELLED`) immediately normalizes and writes to `AppState.academicEvents`. The `syncRuntimeEvents` rehydrates the Calendar Engine, affecting `getTeachingDaysBetween`. This dynamically shifts the `totalClasses` denominator used by the Attendance Engine. The UI reflects the changes instantly across all dates.

### C. Laboratory mutation + Attendance + Persistence
**Observed Behavior:** The Laboratory Engine handles its own `totP` (Total Practical) bounds separately from the theoretical lectures. However, `attendance-engine.js` aggregates these correctly for overall statistics without corrupting the granular laboratory metrics. Modifying lab state correctly sets `AppState.isDirty` and triggers cloud debounce.

### D. Offline Attendance + Reload + Cloud hydration
**Observed Behavior:** An offline mutation is saved in `localStorage` with `isDirty = true`. When the user reloads the app online, `initLocalState` reads the dirty flag. The `fetchCloudStates` pipeline intercepts this and forces a "dirty flush" (set before get), ensuring offline data is safely pushed to Firestore before cloud state overwrites the local state.

### E. Offline Academic Event + Reconnect + Cloud persistence
**Observed Behavior:** Same mechanism as D. The generic `saveStates` architecture in `storage.js` guarantees that `academicEvents` is treated identically to `attendanceData`. Upon reconnect, `pwa.js` detects the `online` event and proactively fires `triggerCloudSync()` (P2 fix applied in S3.7), instantly flushing the local event array to Firestore.

### F. Theme change + Reload + PWA cache
**Observed Behavior:** Theme preferences are stored in `AppState.settings` and persisted to Firestore. Loading the app offline uses the locally cached settings first. The PWA `index.html` loads almost instantly, applying the correct theme before any visible layout shift occurs.

### G. Logout/login + cached local state + Firestore hydration
**Observed Behavior:** `logoutUser` safely clears `localStorage` and `AppState`. A subsequent login hydrates completely from Firestore. No stale local state crosses user boundaries.

### H. Service Worker update + new application version + existing user state
**Observed Behavior:** Bumping `APP_VERSION` registers a new SW query parameter, triggering a fresh install. During activation, old caches are pruned. Because state lives in `localStorage` (and Firestore) rather than the SW Cache Storage, data is 100% resilient across application binary upgrades.
